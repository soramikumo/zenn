### はじめに
本記事は筆者のような資格合格だけを目的とした人に同じ轍を踏んでほしくない目的で執筆しています。
:::message alert
本記事はあくまで筆者個人の体験をもとにした見解であり、資格取得そのものを否定する意図はありません。

対象の読者
- これから資格(SAA含む)取得を行う人、迷っている人

資格を取った時点のスペック、目的
- 業務半年弱、普段業務ではAzureをメインで使っている、インフラ寄りのバックエンド開発
- AWSとAzureはパブリッククラウドとしてどう違うのか、どのようなサービスを提供しているのかが気になってSAAを取得しようと奮起

:::details SAAとは？~サービス問題を添えて~
公式URL: https://aws.amazon.com/jp/certification/certified-solutions-architect-associate/
> AWS Certified Solutions Architect – Associate（SAA-C03）は、AWSでのクラウドアーキテクチャ設計スキルを認定する試験です。対象は1年以上のAWS実務経験者で、コスト・セキュリティ・可用性・パフォーマンスを考慮した設計判断ができるかが問われます。試験は65問・130分・720点以上（1000点満点）で合格です。

AWSのアーキテクトにフォーカスを当てた試験ですね。
試験レベルは3段階あって、アソシエイトレベルは中級です。
SAA以外にも[DVA(Certified Developer - Associate)](https://aws.amazon.com/jp/certification/certified-developer-associate/)や[SCS(Security – Specialty)](https://aws.amazon.com/jp/certification/certified-security-specialty/)などあります。

SAAのサンプル問題

> あなたはソフトウェア会社のクラウドアーキテクトです。開発チームは複数のマイクロサービスをコンテナで運用しており、以下の要件があります。

- 既存のオンプレミス環境でも Kubernetes を使ってコンテナを管理している
- AWS移行後もオンプレミスと 同じ操作方法・マニフェスト形式 を維持したい
- チームには Kubernetes の運用経験者が複数名いる

> この要件を最も適切に満たすAWSサービスはどれですか？

A． Amazon ECS（Fargate起動タイプ）を使用する
B． Amazon EKS を使用する 
C． AWS Lambda を使用してコンテナをサーバーレスで実行する
D． AWS Elastic Beanstalk を使用してコンテナをデプロイする

---
K8s,マニフェスト, コンテナ管理というキーワードからEKS(Elastic Kubernetes Service)になります。連想ゲームみたいなもんです。
:::

試験自体には勉強を開始して2~3週間で合格できました。が
ここが盲点でした。

途中からAWSの理解よりも、合格することに目的が切り替わっていました。主な勉強方法は[Ping-t](https://mondai.ping-t.com/g)だったり、Udemyなどの問題集を解いたりするだけの勉強法でした。

結果、コスパ？タイパ？よく資格合格はできましたが、正直利用経験のないAIサービスに関して全く理解できていませんでしたし、Web周りの覚えるべきサービスに関しても正確に理解しているとは言いがたかったです。

### 合格したのに何もわかっていなかった
資格取得してからすぐに活かせる機会が来ました。
業務でQueueに関する実装を任されたのですが
- FIFOキューと標準キュー、どっちを選ぶべきか？FIFOはどのように順序保証をしているのか
- なぜメッセージが複数回処理される可能性があるのか、重複排除はどう担保するか？
など...

概念は「知っていた」けど実装の判断ができず、全然わかってないやん、、と
Whatは分かっても、HowもWhyもわからない状態でした。

時間が経って気づいたのですが、概念やユースケースを理解していたとて、すぐに技術選定できるわけではなかったです。資格合格で得られる効果を買い被っていたのです。
個人開発レベルであれば問題ないでしょうが、大規模なサービスや厳格な品質が求められるプロダクトにおいては、それ相応の根拠が求められると思います。
そういったときに重要なのは資格で得た知識よりも、実際の経験だったり勘だったりするのですが、やはり泥臭い実装の経験があると全然違うでしょう。

資格勉強のみで得られる表面的な理解は実務には遠く及ばないと、私は感じました。

### じゃあどう勉強するのが良いの？
1. **目的を明確にすること**だと思います。
「合格すること」を目的にした瞬間、勉強方法は問題集を解くだけになります。
それで受かってしまうのが資格の怖いところであり、資格を保有していても理解がが不足していると、効率の悪い勉強を繰り返す悪習慣が出来てしまいます。

目的を「合格」ではなく、「昇給昇格のための短期合格」にするのであれば、今回の勉強法は最適でした。が、理解のためにやっているのであれば、別に長期的にしっかり学習したほうが身になるという話です。

2. **業務で使いそうなサービスに関して深堀ること**です。

私が今思う、やっておけば良かったこと
- SQSを実際に作って、メッセージを送受信してみる
- Lambda + API Gatewayを繋いで動かしてみる
- S3＋CloudFrontを使ってWebサービスをホスティングしてみる

最新の技術を学びたいなら、IaCにも取り組み、CDKとTerraformの違いなどに気づけると良いと思います。

つっても、こんなの羅列しただけの表面的な動作でしかないです。真に理解するには試して自分で仮説をもって取り組み、異なった場合になぜそうなったのかを追求し続けること、実装を見に行くなどレイヤーを変えて深堀り続けることなんじゃないかなと。
その過程は資格勉強よりもよっぽど身になる経験ができると思いますし、それをアウトプットするとさらに記憶に色濃く残ると思います。

資格勉強からは遠回りですが確実に自力が付きますし、知らない概念を知り深堀る過程こそが資格勉強の醍醐味なような気もします。

### 取ってみたあとの気づき
1. 資格に過度な期待はしないこと。
SAAはAWSを理解する資格ではなく、**AWSで設計するための考え方の入口でしかない**です。
これを取ったから評価が上がるわけでも、案件参入する切符にもならないと考えるのが無難です。
上長と直接面談するほうが、効果的だと思いますよ

2. 技術だけで解決できる問題は少ない
技術的理解と、同じくらいドメイン知識が求められるということです。Well-Architectedをそのまま反映できるほど、世の中はシンプルではないという学びもありました

### AI時代なら手を動かす必要ないんじゃ？
深掘ろうとは言ったものの、AI時代では概念さえ理解しておけば実装をAIに任せるという判断は合理的な気もします。
CLIで権限設定してAgentを動かせば、自然言語で操作して構築してくれますし、クラウドサービス自体もどんどん抽象化されて行っています。

ただ2つ落とし穴があると思っています。

1. 出力の正誤が判断できないこと。
AIが生成したコードや構成が正しいかどうかは、サービスへの理解がなければレビューができません。
なんとなくわかっている状態で鵜呑みにすると、
作ったあとに何も語れないAI使いになってしまうのと、
バグや脆弱性を抱えたまま外部公開するリスクがあります。

3. 良い設計ができないこと。
AIは指示した通りに動くものを作りますが、コスト・可用性・セキュリティのトレードオフを判断するのは人間です。理解が浅いままだと、動くけど設計として筋の悪いものが出来上がるリスクがあります。
その後のコスト最適化の判断など、自分で成長の機会を摘んでしまっているような気がします。

自分の頭で考えて、試行錯誤してノウハウが溜まっていくことで身についていくのかなぁと感じました。
**補助**としての利用範囲を超えて言いなりになってしまいがちだなという啓蒙警鐘を込めて

読めるだけではそこまで活きないのですが、インフラの人とコミュニケーションは容易になります。
またAzureには構成図を書く風習が多くないので、こういった文化は実務でも輸入しています。

それと曖昧な理解だったサービスを知れたのは良かったです。
具体的にはIAMやCognitoなど、個人開発ではそこまで意識しない領域、かつ実務では必須級のサービスについて学べたのはよかったです。
知る知らないの差は結構大きいと思います。権限周りは初心者が意外と見落としがちな設計概念の一つなので。

### おわりに
SAAは取って損はないですが、それ以上でもないです。

資格は「わからないことを**少しわかる**」ようにしてくれますが、「**できる**」ようにはしてくれません。その先は自分で手を動かすしかないですし、それを資格取得後にやるくらいなら最初からやれという話でもあります。

結局自分が欲しかったのは合格の実績ではなく、「あのサービスどう動いてるんだろう」と気になって手を動かし続ける習慣だったんだと今は思います。それに気づけたのが、この資格を取って一番よかったことかもしれません。ちゃんちゃん
